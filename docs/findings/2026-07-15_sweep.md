## Item 1 (B2): `students.balance_due`

**State: already fixed. The brief's premise is stale.** The codebase has been
refactored off any stored `students.balance_due` column. No code in `src/` writes
or selects that column against the students table. The ~17-30 textual matches for
`balance_due` are all one of: an in-memory response/prop field name populated from
a live-computed balance, a WhatsApp template name (`chq_parent_balance_due`), an
i18n key (`ts('balance_due')`), or a comment.

Single source of truth: **`src/lib/studentBalance.ts`** (`getStudentBalances`,
`getStudentBalance`, pure `computeBalance`, `sumOutstanding`). Its docstring
(lines 33-35) is explicit: "There is deliberately NO stored `students.balance_due`
column (it never existed - selecting it made PostgREST 400 the whole query).
Every screen must compute through this helper." Balance = sum of chargeable
center-group `attendance_scans.charged_fee` minus sum of `payments.amount` in
{confirmed, pending, paid}.

What actually happens today, per reference class:

- **The write the brief worried about does not exist.** `src/app/api/payments/confirm/route.ts:69-72`
  is only a comment: "we do NOT write a stored balance here ... the old decrement
  was dead code ... Balance is always computed on read." The route updates
  `payments.status='confirmed'` and returns 200. There is no balance write to
  fail, so a payment confirm never 500s on this account.
- **No `.select()` reads the column.** `src/app/[locale]/students/[id]/page.tsx:46-52`
  hard-codes `STUDENT_SELECT` to physical columns with a guard comment warning
  that selecting `balance_due` would 400 the whole query and surface as "student
  not found". Because nothing queries the column, the absent column has zero
  runtime effect.
- **List view** computes live: `src/app/[locale]/students/page.tsx:389-392`
  (`getStudentBalances`, stored into `balanceByStudent`). `:1721` is an i18n label
  key, not a column.
- **Detail page** shows NO balance card at all: it renders only `visits` and
  `lastSeen` KpiCards (`students/[id]/page.tsx:456-462`).
- API consumers (`analytics/revenue`, `students/at-risk`, `parent/portal`) and
  UI (`ScanTab`, `PrintStatementModal`, `AtRiskPanel`, `StudentBalanceStatement`)
  all populate a field literally named `balance_due` from the computed map, never
  a DB read.

**Recommendation:** Adopt the live-recompute direction (the brief's option B). It
is already implemented, documented, and drift-free; **no migration, no backfill,
no column** is warranted (option A would reintroduce the exact drift risk the
helper was built to remove). Two small, optional follow-ups:
1. Add a Balance card to the student detail page using `getStudentBalance` (the
   detail page currently shows none). This is the only user-visible gap. Product
   decision, small UI change.
2. Add a build-time guard (mirroring the existing `check:*` gates) that fails if a
   students `.select(...)` string ever contains `balance_due`, so the
   PostgREST-400 "student not found" footgun can never regress. (Idea from the
   sweep; the safety today rests only on the guard comments.)

**Guesses / limits:** I did not open all ~30 grep hits, only the load-bearing
writes/selects/computes; the rest are classified non-DB by grep context. I read
the current code, not the git history, so "recently refactored" is inferred from
the comments, not proven against commits.

## Item 2: Commission engine

**State: both reported bugs are already fixed by the recent rewrite.** (0
commission rows exist, so nothing has run in production yet; this is a code audit.)

- **Bug (a), clawback fires on cancellation instead of chargeback: FIXED.**
  Clawback (setting tiers to `clawed_back`) happens only inside
  `clawbackCommissionsForOwner` (`src/lib/commissions.ts:387-455`), whose only
  caller is `finalizeInvoiceChargeback` (`src/lib/invoicePaymobPayment.ts:702-711`),
  which is reached only when the Paymob webhook sees `is_voided`/`is_refunded`
  (`src/app/api/paymob/webhook/route.ts:53-63`). Cancellation, suspension, and
  blacklist run different paths and explicitly do NOT claw back
  (`src/app/api/admin/centers/[id]/route.ts:532-534`: "blacklisting is an admin
  ban, NOT a payment chargeback - it must NOT claw back commission").
- **Bug (b), teacher reassignment unwired: FIXED.** `reassignCommissions`
  (`src/lib/commissions.ts:258-385`) voids the outgoing rep's still-live tiers to
  `reassigned`, re-creates rows for the incoming rep, transfers the payment clock,
  and recomputes the manager override. It is wired to both admin assignment PATCH
  routes on a `staff_id` change: `center-assignments/[id]/route.ts:122-135` and
  `teacher-assignments/[id]/route.ts:85-100`.
- **Promo-awareness:** the T1 (first) half **is** promo-aware: base = standing
  monthly price times (1 - promoFraction), where `firstPaymentPromoFraction`
  reads real invoice amounts (`src/lib/commission/ownerFinancials.ts:59-109`;
  rep rate 20% split into equal T1/T2 halves in `commission/rates.ts:54-58`). The
  T2 (second) half is deliberately promo-UNAWARE: it is recomputed at the current
  standing price at the 6-month mark. That is correct only if promos are
  signup-only.

Residual observations (design, not defects):
- A change to only the manager/reports-to on an assignment (not `staff_id`) does
  not recompute an existing override to the new manager (it falls to the
  idempotent create path).
- The T2 full-price recompute assumes promos never apply beyond signup.
- `firstPaymentPromoFraction` silently resolves to 0 (full-price base) if a promo
  invoice lacks `promo_original_amount`.
- Clawback is non-blocking at the call site (try/catch that console.errors,
  `invoicePaymobPayment.ts:712-714`), though it Sentry-captures and rethrows on a
  rejected UPDATE inside the function.

**Recommendation:** Treat both reported bugs as resolved; no fix required. For
defense-in-depth, add tests asserting clawback fires on an `is_voided`/`is_refunded`
webhook and NOT on blacklist/cancel/suspend, and that `reassignCommissions`
voids-to-`reassigned` and transfers the clock without double-paying a terminal
tier. Confirm promos are signup-only; if not, revisit T2.

**Guesses / limits:** "promos are signup-only" is asserted by code comments
(`ownerFinancials.ts`, `rates.ts`); the end-to-end promo-application path was not
fully traced. "0 commissions have run" relies on the verified live count.
