## Local schema tooling note (important)

Prod is Postgres **17**; the only local server binary is Postgres **16**. The
baseline migration grants the PG17-only `MAINTAIN` privilege, which PG16 rejects,
so a raw `npm run schema:snapshot` cannot run here. `MAINTAIN` is a
PostgreSQL-specific privilege that `information_schema` never surfaces, so it is
absent from `db/schema.snapshot` on PG17 too. I therefore rebuild locally by
stripping the `MAINTAIN` token **only at apply time** (never touching any committed
file) and confirmed the result is **byte-identical** to the committed snapshot
before adding anything. The snapshot is regenerated by this method, not hand-edited.
CI (`schema-drift.yml`, `postgres:17`) rebuilds from the migrations unchanged.

## 1. Referral recording bug — `referral_commissions` shape vs. code

`referral_commissions` (0 rows) was out of sync with every writer/reader:

- **`referred_center_id` did not exist** — both the cron
  (`api/cron/referral-automation`) and `api/referrals/process-commission` insert it,
  and `api/admin/referrals/commissions` reads a referred center id. First real
  insert would `42703` error.
- **`period_month` was `date NOT NULL`** but all writers pass `'YYYY-MM'` text and
  all readers (`generateInvoicePdf`, `settings/referrals`, admin pages) treat it as
  `'YYYY-MM'`. `'2026-06'::date` is a `22007` error. The sibling table
  `referral_reward_records.period_month` is already `text`.
- **`months_since_activation integer NOT NULL`** is populated by neither writer, so
  even past the two errors the insert would `23502`. It is a meaningful column
  (the commission's month number), so the fix populates it rather than dropping it.

Fix: migration adds `referred_center_id uuid` (FK to `centers(id)` + index, mirroring
`referrer_center_id`) and switches `period_month` to `text`; both inserts now set
`months_since_activation`. The admin quarter filter boundaries were switched from
`YYYY-MM-01` to `YYYY-MM` so lexical text comparison includes the first month.

## 2. Route conflict `api/join/[center_code]` vs `api/join/[groupId]`

Two differently-named dynamic segments at the same level — Next.js rejects this and
`next dev`/`build` crash. The two flows are distinct: `[center_code]/[group_id]` is
the center-code roster join; `[groupId]/{send,verify}-otp` is private-group OTP
self-enroll. The page routes are already `join/[center_code]/[group_id]` and
`join/g/[groupId]`. Fix: move the OTP API routes under `g/` to mirror the page
(`api/join/g/[groupId]/{send,verify}-otp`), leaving one dynamic segment at
`api/join/`. Client fetch URLs updated to match.

## 3. Drop dead `pin_code` column — FLAGGED, NOT dropped (load-bearing)

> UPDATE (verified live 2026-07-18): this was subsequently carried out. `public.users.pin_set_at timestamptz` was added as the authoritative "PIN is set" signal, all four readers migrated to it, and `pin_code` was **DROPPED** (migration `20260701150506_drop_pin_code`). Live `public.users` has **no `pin_code` column** — it now carries `phone`, `role`, `pin_set_at` (verified live 2026-07-18). So the "recommend keeping `pin_code`" conclusion below is historical; see `docs/PIN_SET_CLEANUP_FINDINGS.md` for the execution.

Introspected every reference. `pin_code` is NOT the login credential — the real PIN
is the Supabase Auth password (`set-initial-pin` writes it via
`auth.admin.updateUserById`, login verifies against it). BUT `pin_code IS NULL /
NOT NULL` is the load-bearing **"has this owner finished PIN setup?"** signal, and
there is no alternative (`public.users` has only `pin_code`, `pin_attempts`,
`pin_locked_until` — no `pin_set_at`/`has_password`; Supabase Auth exposes no clean
"password is set" flag). It gates:

- `set-initial-pin` — the double-set guard (refuses `pin_already_set`), which stops a
  stale cookie/leaked fallback link from re-setting an already-set PIN.
- `request-pin-setup-link` — refuses to issue a WhatsApp Set-PIN link if a PIN exists.
- `signup/pin-setup-readiness` and `set-pin` page — readiness / redirect gating.

Per the brief's guardrail ("if any reference turns out to be load-bearing for auth,
STOP and flag it instead of removing"), I did **not** drop it. Dropping it safely
would require first introducing an explicit lifecycle flag (e.g. `pin_set_at`),
migrating all four readers to it, verifying, and only then dropping `pin_code` — a
separate, auth-touching change that should be its own reviewed PR, not folded into a
loose-ends pass. Recommend keeping `pin_code` until that lands.

## 4. Migrate hand-rolled-auth routes to the shared gate

Classified all hand-rolled routes end to end (mechanism, needed identity, correct
target helper, behavioral nuances).

**Migrated to `requireCenterAuth` (12 routes)** — unambiguous center-scoped routes;
each drops a bespoke `getUser`→`users`→`center_id` helper and gains the shared gate's
suspension/blacklist enforcement + authoritative super-admin handling. Original
role/permission checks were reproduced exactly (no behavior change for valid users):

- `parent-pack/toggle`, `parent-pack/status`, `parent-pack/student/[id]`
- `whatsapp-pack/settings`, `whatsapp-pack/student/[studentId]`
- `parents/request-consent`, `students/re-enrollment-campaign`
- `students/pending`, `students/pending/[id]/reject`
- `referral`, `dashboard/send-daily-summary`, `permissions`

**Deliberately left (with reason)** — migrating these would change behavior:

- `onboarding/first-student` — already mirrors `centerAuth` but with **default-true**
  `can_manage_students` semantics on a column that isn't in the shared
  `CenterPermissions` type; the shared gate would default it false.
- `billing/initiate-payment` — the pay-to-reactivate path; must allow suspended
  centers (`allowSuspended`) and reads `users.phone`/`name`, which the gate doesn't
  return.
- `analytics/revenue` — intentionally permits a super-admin with `center_id = null`
  (aggregate view); the gate returns `NO_CENTER_ID` there.
- Org-context routes (`at-risk`, `branches`, `benchmarks`, `analytics/consolidated`,
  `center-users`) — resolve a center from `organization_id`, which the gate doesn't do.
- Pre-center auth flows (`onboarding`, `signup/complete`, `accept-invite/complete`,
  `auth/check-invite`) — the user has no center yet.
- Special/hybrid (`me`, `realtime/subscribe`, `billing/payg-calculate`) — identity
  endpoint / cookie-or-bearer / cron-compatible; not center-operation gates.
- `admin/*` routes are already gated via `getAdminContext`/`requireSuperAdminApi`.

Login path (`centerAuth.ts`, `proxy.ts`, `/api/auth/*`, admin gates) was **not**
touched; migrated routes call the existing shared gate unchanged.
