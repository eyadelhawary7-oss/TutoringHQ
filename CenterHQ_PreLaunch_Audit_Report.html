4. Systemic Patterns (Root Causes)

Pattern A: Inconsistent Arabic-Indic numeral formatting

Affects: /ar/benchmarks, /ar/settings, /ar/settings/billing, /ar/settings?tab=team, /ar/groups, /ar/admin (and likely all other /ar/ pages with dynamic numbers)

Root cause: Number formatting is inconsistent across components. Some components (e.g., pricing cards on /ar/groups showing ج.م ٢٠٠, MRR on /ar/admin showing ٢١,٠٠٠) correctly use Arabic-Indic numerals, while others (KPI counters, percentage values, count labels) output Western digits. This suggests the locale-aware formatter is applied in some code paths but not others — likely a missing Intl.NumberFormat('ar-EG') or equivalent wrapper on certain components.

Recommendation: Create a shared formatNumber(value, locale) utility and audit every component that renders numeric data to use it. A global search for hardcoded .toString() or template literal number interpolation in Arabic-context components should catch most instances.

Pattern B: Date pickers not localized for Arabic

Affects: /ar/attendance, /ar/payments (and likely any page with date range selectors)

Root cause: The date picker component renders "12-Apr-2026" regardless of locale. It does not use Arabic month names or Arabic-Indic numerals.

Recommendation: Configure the date picker library (likely a custom or third-party component) to accept a locale prop and format dates using Intl.DateTimeFormat('ar-EG').

Pattern C: Missing i18n keys for relative time / status strings

Affects: /ar/admin?tab=centers ("Never", "days ago"), /ar/branches (English description text)

Root cause: Some strings were never added to the Arabic translation file. These are typically edge cases (empty states, relative time formatters, upgrade prompts).

Recommendation: Run a comprehensive scan of all i18n keys to find untranslated entries. Use i18next-scanner or equivalent tooling to detect missing translations.
